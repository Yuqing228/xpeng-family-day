# 乐牛（LEOPEN）接口说明 · 含实测案例

适用场景：小鹏家年华活动，员工/家人凭工卡余额在摊位消费，由本应用调用乐牛接口完成扣款、查询。

- 数据来源：2026-10-26 在妙搭沙箱对 `anniversary-homefair-api.x-peng.com` 的真实调用抓包，请求/响应报文均为原文（`appsecret` 从不回显，已脱敏为 `***`）
- 覆盖接口：工卡扣款 `pay/device`、订单状态查询 `order/state/query`、钱包余额查询 `account/balance/query`、查询用户信息 `customer/query`
- 四个接口当前全部实测通过（`code=10000`）

---

## 0. 结论速览

| 接口 | 路径（相对域名） | content 字段 | 实测状态 |
|---|---|---|---|
| 工卡扣款 | `/tengyun-api/leopen/pay/device` | 六字段，key 必须 ASCII 升序 | 通过，真实扣款 1 分成功 |
| 订单状态查询 | `/tengyun-api/leopen/order/state/query` | `macOrdId` | 通过 |
| 钱包余额查询 | `/tengyun-api/leopen/account/balance/query` | `custId` | 通过 |
| 查询用户信息 | `/tengyun-api/leopen/customer/query` | `custNum` | 通过 |

最容易踩的三个坑，按严重度排序：

1. **content 的 key 必须严格 ASCII 升序**，顺序错一律 `100042 签名错误`（详见面 1.4）
2. **入口必须带 `/tengyun-api` 前缀**，否则整站返回 25 字节「无权限访问该页面」，与签名无关
3. **`machineSn` 必须是已注册的设备序列号**，填设备名会返 `40004 设备不存在`

## 1. 通用协议

### 1.1 入口

```
POST https://anniversary-homefair-api.x-peng.com/tengyun-api/leopen/<接口>
Content-Type: application/json
```

真实入口是上述域名下的 `/tengyun-api` 段。去掉 `/tengyun-api` 会命中前置鉴权层，返回 25 字节 HTML 文本「无权限访问该页面」，HTTP 200，很容易被误判成签名问题。

### 1.2 外层请求报文

```json
{
  "appid": "629230940945653760",
  "content": { "...接口各自的业务字段..." },
  "nonce": "1793001470230372128",
  "sign": "C9DD21235D981956680C89CE6959462F",
  "signtype": "md5",
  "timestamp": "1793001470230",
  "version": "5.43.4.12"
}
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `appid` | string | 是 | 应用凭证，家年华活动为 `629230940945653760` |
| `content` | object | 是 | 各接口业务字段。**请求体里是对象；算签名时要先序列化成字符串** |
| `nonce` | string | 是 | 随机串，建议随机长度 ≤ 20 位数字串 |
| `sign` | string | 是 | MD5 大写十六进制，算法见 1.3 |
| `signtype` | string | 是 | 固定 `md5` |
| `timestamp` | string | 是 | 毫秒时间戳字符串（13 位） |
| `version` | string | 是 | 四接口统一 `5.43.4.12`（2026-10-26 15:57 全量复验通过）；`1.0.0` 历史实测亦通过，服务端不校验 version 白名单。version 参与签名，两端必须一致 |

### 1.3 签名算法（照抄）

签名串由固定顺序的 7 段拼成，`&` 连接，**末尾拼 appsecret 且 appsecret 不参与 key=value 形式**：

```
appid=<appid>&content=<content 的 JSON 字符串>&nonce=<nonce>&signtype=md5&timestamp=<timestamp>&version=<version>&appsecret=<appsecret>
```

```
sign = MD5(上述字符串).toUpperCase()
```

实测样例（工卡扣款）：

```
signStr = appid=629230940945653760&content={"amount":0,"custId":"489273400569634816","macOrdId":"JNH1128-0001-1793001470345","machineSn":"5m6665785","nuClearMode":2,"ordTime":"2026-10-26 15:57:50"}&nonce=1793001470230372128&signtype=md5&timestamp=1793001470230&version=5.43.4.12&appsecret=***
sign    = C9DD21235D981956680C89CE6959462F
```

注意两个细节：

- `content` 参与签名时是**紧凑 JSON 字符串**（无空格、无换行），且 key 顺序即签名依据，不能重新排序后再拼
- 段顺序固定为 `appid → content → nonce → signtype → timestamp → version → appsecret`，不按字母序

### 1.4 content 的 key 必须 ASCII 升序（头号坑）

服务端验签时会把你提交的 `content` **按它自己的规则（key ASCII 升序）重新序列化**，再用同一套算法算一遍 sign 比对。所以你提交的字节序不是它期望的顺序，重算必然对不上，直接 `100042`。

工卡扣款 `pay/device` 的正确顺序：

```
amount → custId → macOrdId → machineSn → nuClearMode → ordTime
```

逐字符比较依据：`a(97) < c(99) < m(109,a) < machineSn < n(110) < o(111)`，注意 `macOrdId` 与 `machineSn` 都以 `m` 开头，第二位 `a(97) < a...`，实际按整串比较 `macOrdId` 在前。

**反例（实测报错的那一版）**：

```json
{"amount":1,"nuClearMode":3,"custId":"489273400569634816","macOrdId":"...","machineSn":"...","ordTime":"..."}
```

`nuClearMode`（n=110）排在 `custId`（c=99）前面，顺序错，返回：

```json
{"code":100042,"msg":"签名错误"}
```

把顺序调正后，content 一个字段都没改，立刻通过。这条是硬要求，不是建议。

单字段接口（`order/state/query`、`account/balance/query`、`customer/query`）只有一个 key，不受排序影响。

### 1.5 结果判定

**HTTP 200 不代表成功。** 业务结果全部在响应体的 `code` 里：

| code | 含义 | 说明 |
|---|---|---|
| `0` 或 `10000` | 成功 | 两个都要认，实测这几个接口返回的是 `10000` |
| `100042` | 签名错误 | 先查 content key 顺序，再查 signStr 拼接、appsecret、content 序列化 |
| `40004` | 业务参数错误 | 具体看 `msg`，例如「设备不存在,请重试」「人员id和第三方人员id不可都为空」 |
| 25 字节「无权限访问该页面」 | 入口错 | 缺 `/tengyun-api` 前缀 |

响应头带 `x-trace-id`，排查网关问题时直接把这个值给小鹏运维。

## 2. 接口一：工卡扣款 `pay/device`

### 2.1 请求入参（content）

**该接口会真实扣员工卡里的钱**，联调/测试务必按 2.5 的金额策略来。

| 字段 | 类型 | 必填 | 实测取值 | 说明与坑 |
|---|---|---|---|---|
| `amount` | number | 是 | `0`（联调）/ `1`（实扣案例） | **单位是分**，`1` = 1 分钱、`0` = 不扣钱。传 `0.01` 会被当成 0.01 分。**联调默认用 0**（见 2.6） |
| `custId` | string | 是 | `489273400569634816` | 乐牛人员 ID，由 `customer/query` 用工号换取；**必须字符串**，走 JS 数字会丢精度 |
| `macOrdId` | string | 是 | `JNH1128-0001-1792999666248` | 商户订单号，业务侧唯一。长度 ≤ 40，建议每次新生成，重复有可能被幂等拦下 |
| `machineSn` | string | 是 | `5m6665785` | **必须是乐牛已注册的设备序列号**。填设备名称（如「open支付专用设备-小鹏家年华对接」）会返 `40004 设备不存在` |
| `nuClearMode` | number | 是 | `2` | 结算模式。`3` 与 `2` 都验签通过，语义待业务方确认，当前按 `2` 使用 |
| `ordTime` | string | 是 | `2026-10-26 15:27:46` | 下单时间，北京时间 `yyyy-MM-dd HH:mm:ss`，不要带毫秒与时区后缀 |

content 的 key 顺序即 2.1 表格顺序（ASCII 升序），不能按习惯重排成 `amount → nuClearMode → custId...`。

### 2.5 坑清单

1. **content key 顺序**：错序必 `100042`，字段一个不缺也没用（见 1.4）
2. **`machineSn` 填设备名**：`{"code":40004,"msg":"设备不存在,请重试","data":null}`，必须用已注册序列号 `5m6665785`
3. **`amount` 单位是分**：业务侧算好的金额如果已经是分，直接传；如果按元算要 `× 100`
4. **`custId` 精度**：`489273400569634816` 超过 JS 安全整数范围，任何环节都不能数字化，全程字符串
5. **验签先于参数校验**：字段缺失、字段错序都先报 `100042`，不会告诉你少了哪个字段，只能自己逐个对
6. **`ordTime` 时区**：必须北京时间字符串；用 `toISOString()` 会产生 `T`/`Z`，格式不符
7. **重复 `macOrdId` 有幂等风险**：同一单号重试可能被服务端判重，业务侧重试用新单号、用 `order/state/query` 确认原单
8. **`macOrdId` 长度**：列定义 40，`JNH1128-0001-<13 位时间戳>` 共 26 位，安全
9. **`mealCode` 非固定**：实测 001 → 002 递增，落库或展示不能用常量

### 2.6 测试金额策略：一律用 0 分（已验证可行）

这是真实扣款接口，扣的是员工自己的钱，**测试金额从 1 分降为 0 分**：

```json
"amount": 0
```

已实测（2026-10-26 15:47:05）：0 元下单 `code=10000`、`realAmount=0`，扣款前后余额三项完全相同（`3361 / 403 / 3764` 未变），服务端照常生成订单号。完整报文见 2.4。

标准测试流程：

1. 先 `account/balance/query` 记录扣款前 `walletBal` / `subsidyBal` / `accBal`
2. 用 `amount: 0` 下单，确认返回 `code=10000`
3. 再查一次余额，确认三项数值未变
4. 用返回的 `macOrdId` 调 `order/state/query` 确认订单存在、金额为 0
5. 全程不产生真实扣款

结论：签名、字段口径的任何回归测试都用 0 分跑。只有必须验证「非零金额真实扣减」时才用 `amount=1`，且只在必要时打一次。

### 2.7 实测失败案例

设备序列号传成设备名时：

```json
{"code":40004,"msg":"设备不存在,请重试","data":null}
```

content key 错序时：

```json
{"code":100042,"msg":"签名错误"}
```

两种情况都**没有扣款**，服务端在业务执行前就拦下了。

## 3. 接口二：订单状态查询 `order/state/query`

只读接口，扣款超时/重试前用它确认结果，避免重复扣款。

### 3.1 请求入参（content）

| 字段 | 类型 | 必填 | 实测取值 |
|---|---|---|---|
| `macOrdId` | string | 是 | 商户订单号，如 `JNH1128-0001-1792999666248` |

### 3.2 实测案例

请求（2026-10-26 15:57:45，version `5.43.4.12`）：

```json
{
  "appid": "629230940945653760",
  "content": { "macOrdId": "JNH1128-0001-1793000825328" },
  "nonce": "1793001465157470362",
  "sign": "F37F6BB155A900AB030B17F6CDE5FD08",
  "signtype": "md5",
  "timestamp": "1793001465157",
  "version": "5.43.4.12"
}
```

响应（`code=10000`，`x-trace-id: d8061dccdc9837307d6fd64a33adfb06`）：

```json
{
  "code": 10000,
  "msg": "成功",
  "data": {
    "ordId": "638629363444621313",
    "macOrdId": "JNH1128-0001-1793000825328",
    "payState": 3,
    "ordState": "1",
    "totalAmount": "0",
    "realAmount": "0",
    "payTime": "2026-10-26 15:47:05",
    "orderDate": "2026-10-26"
  }

```

### 3.3 坑清单

1. **类型不统一**：`payState` 是数字 `3`，`ordState` 是字符串 `"1"`，`totalAmount` / `realAmount` 是字符串 `"1"`。前端/落库解析不能统一按一种类型处理
2. **枚举语义未确认**：`payState=3`、`ordState="1"` 的确切含义业务方没有给字典。金额、`payTime`、`ordId` 与该单扣款返回完全一致，可判定这笔已成交，但状态码不要自己猜着写进业务分支，要业务方确认
3. **查不存在的单号行为未实测**：不要假设一定返回空数据或 `code=10000`
4. **`ordId` 与扣款返回一致**：可用 `ordId` 或 `macOrdId` 任一作为对账键，实测两者一一对应

## 4. 接口三：钱包余额查询 `account/balance/query`

### 4.1 请求入参（content）

| 字段 | 类型 | 必填 | 实测取值 |
|---|---|---|---|
| `custId` | string | 是 | 乐牛人员 ID，如 `489273400569634816` |
| `custThirdId` | string | 否 | 第三方人员 ID，如 `1940727940883533827`，与 `custId` 二选一 |

**只认 `custId` / `custThirdId`**。传 `mobile` 或 `custNum` 会返回：

```json
{"code":40004,"msg":"人员id和第三方人员id不可都为空","data":null}

```
工号 → customer/query → custId → account/balance/query → 余额

必须先换 `custId`，没有一步直达的按工号查余额接口。

## 5. 接口四：查询用户信息 `customer/query`

工号换取 `custId` 的唯一入口，下单和查余额的前置。

### 5.1 请求入参（content）

### 5.3 关键字段

| 字段 | 说明 |
|---|---|
| `custId` | 乐牛人员 ID，扣款/查余额都靠它 |
| `custThirdId` | 第三方人员 ID，可替代 `custId` 使用 |
| `custNum` | 工号 |
| `serialNum` | 工卡号（如 `E5413B23`），用于工卡识别 |
| `cardStatus` | 卡状态，`1` 正常 |
| `accStatus` | 账户状态，`1` 正常 |
| `custState` | 人员状态，`1` 正常 |
| `cardList[]` | 该人持有的所有卡，多卡时需按 `serialNum` 区分 |

### 5.4 坑清单

1. **`count` 是字符串** `"1"`，不是数字，做 `> 0` 判断前先转换
2. **大量字段为 null**：`idCard`、`age`、`birthday`、`job`、`custPhotoUrl`、`endDate` 实测均为空，前端不能直接渲染
3. **`wechatOpenid` 是空字符串**而非 null，判断空值要兼容两种
4. **`mobile` 涉及个人隐私**：日志和页面上不要明文落库、不要回显
5. **一人多卡**：`cardList` 可能多元素，取卡信息别写死 `customerList[0].serialNum`
6. **按工号可能查无此人**：`customerList` 为空数组时 `count` 为 `"0"`，要有明确空态，别当异常抛出

## 6. 端到端联调顺序

```
① 工卡/工号拿到 custNum
        ↓  customer/query
② custId（+ serialNum / cardStatus / accStatus）
        ↓  account/balance/query
③ 校验余额 >= 本次金额，accStatus = 1
        ↓  pay/device（新 macOrdId，金额分，machineSn=5m6665785）
④ code=10000 → 记 ordId / realAmount / payTime / ordQrCode
        ↓  落 payment_ledger（macOrdId 唯一索引）
⑤ 超时或网络异常时：order/state/query 用原 macOrdId 反查，确认后再决定是否重试
```

对账三件套：`macOrdId`（自己生成的，唯一）、`ordId`（乐牛返回的订单号）、`payTime`（双方时间一致）。

## 7. 排障速查表

| 现象 | 根因 | 处置 |
|---|---|---|
| 25 字节「无权限访问该页面」 | 路径缺 `/tengyun-api` | 补全前缀 |
| `100042 签名错误` | content key 非 ASCII 升序 | 按接口逐字段排正序，重新序列化 |
| `100042 签名错误` | signStr 拼接顺序错 / appsecret 错 / content 带空格 | 按 1.3 模板逐段核对，content 用紧凑 JSON |
| `100042 签名错误` | 缺字段 | 验签先于参数校验，缺字段也报这个，只能自己逐个对 |
| `40004 设备不存在,请重试` | `machineSn` 填了设备名 | 改用已注册序列号 `5m6665785` |
| `40004 人员id和第三方人员id不可都为空` | 余额查询传了 `mobile` / `custNum` | 改成 `custId` 或 `custThirdId` |
| 金额被放大 100 倍 | 把分当元传 | `amount`、`walletBal` 等全部是分 |
| `custId` 末位变 0 | JS 数字精度丢失 | 全程字符串，禁止 `Number()` |
| 回写订单号冲突 | 重试复用 `macOrdId` | 重试换新单号，原单走 `order/state/query` 确认 |
